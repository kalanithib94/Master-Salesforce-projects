What changed (vs v1.3.0):
  Reviewer feedback: while the user was on the **ABC Corporation Inc.**
  Account record page and asked "Provide the account details", the agent
  replied with a synthetic search result ("No Account found matching the
  current record") instead of using the page-context Account Id with
  fetch_account_details. Root cause was twofold: (a) the
  Prompt_Command__c JSON schema for fetch_account_details only declared
  `account_name` (required), so the LLM physically could not pass the
  page-context Id even with perfect prompt guidance; (b) the system prompt
  declared page context as Rule 2 priority #1 but never operationalised
  HOW to use it — no parameter names, no "first action" pattern, no
  examples.

  This patch addresses (b). The companion schema fix for (a) is applied
  in the org's ccai__AI_Prompt__c record for fetch_account_details
  (and documented in GPTfy_Agent_Prompt_Commands.md §1.2).

  RULE 2 — KNOW WHICH RECORD:
   1. NEW "CRITICAL — Using the record Id from page context" sub-section
      after the priority list, mirroring the pattern from
      Sample system prompt.txt that already worked for Opportunity. New
      block documents:
        * Object Id prefixes (Account 001…, Contact 003…, Lead 00Q…,
          Opportunity 006…, Case 500…) so the LLM can recognise the
          page-context Id format.
        * The exact per-object parameter name to pass the page-context Id
          under (account_id / contact_id / lead_id / opportunity_id /
          case_id) for every skill that accepts a record Id.
        * Three "page-context fast paths" — for details requests,
          updates, and activity logging — that explicitly say to call
          fetch_/update_/log_ skills with the Id directly, without first
          calling fuzzy_search_*.
        * A fallback rule: if the runtime did NOT inject a page record
          Id, fall back to priority steps 2–4. NEVER fabricate an Id and
          NEVER paraphrase "the current record" as a search term.

  EXAMPLES appendix:
   2. NEW EXAMPLE 4 — "Page-context-driven details fetch (Account record
      page)": fully-worked dialogue showing the user on ABC Corporation
      Inc., asking "Provide the account details", and the assistant
      calling fetch_account_details with `{ account_id: "001..." }`
      directly — no fuzzy search, no name resolution.
   3. NEW COUNTER-EXAMPLE block immediately after Example 4: shows the
      exact failing behaviour from the screenshot ("No Account found
      matching the current record") and explicitly labels it as INCORRECT.
      LLMs are biased to copy patterns; explicitly showing the wrong
      pattern + correct pattern side-by-side is the strongest available
      mitigation.

  Metadata:
   4. Header bumped to "Version: 1.3.1 | Last updated: 2026-05-08".

  Net char delta vs v1.3.0: roughly +4,200 chars (LF-normalised).

Why:
  - Production user feedback: page-context-driven flows (the most common
    way users ask the agent to do things from a record page) were silently
    broken for Account because fetch_account_details's Prompt_Command__c
    schema didn't expose account_id. Even after fixing the schema, the
    LLM needed an explicit prompt-level instruction + worked example to
    reliably USE the new parameter; otherwise it would still default to
    name-based reasoning out of habit.
  - The counter-example pattern (Example 4 + COUNTER-EXAMPLE block) is a
    deliberately heavyweight mitigation because page-context handling is
    high-value and high-frequency. We will re-evaluate after a week of
    production usage and trim if no regressions.

Companion changes (NOT in this snapshot):
  - GPTfy_Agent_Prompt_Commands.md §1.2: fetch_account_details schema
    now exposes both account_id and account_name with anyOf required.

HOW TO REVERT
═══════════════════════════════════════════════════════════════════════════════

1. To revert the working file in the repo to a previous version:
       Copy-Item docs\system-prompt-versions\v<X.Y.Z>__<date>__<slug>.txt `
                 docs\GenericCRMAssistant_SystemPrompt.txt -Force
   (PowerShell, run from the Deliverables folder.)

2. To re-sync the All-in-One agent's ccai__System_Prompt__c field to whatever
   is currently in docs/GenericCRMAssistant_SystemPrompt.txt:
       powershell -ExecutionPolicy Bypass -File scripts\SyncSystemPromptToOrg.ps1
   (Pass -AgentId <Id> to target a different agent.)
   The script bakes the file content into a one-shot anonymous Apex update,
   runs it via `sf apex run`, and verifies the stored char length matches.
   A 1-char "trim-trailing-newline" delta is expected and treated as success.

3. To verify the org currently matches a specific version:
       sf apex run --file scripts\PullOrgSystemPrompt.apex
       powershell -ExecutionPolicy Bypass -File scripts\DecodeOrgSysprompt.ps1 `
                 -OutputPath _temp_org_dump.txt
       fc /B _temp_org_dump.txt docs\system-prompt-versions\v<X.Y.Z>...txt
       Remove-Item _temp_org_dump.txt
